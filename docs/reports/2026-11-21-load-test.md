# Синхронизация: три бага с устройства и нагрузочный тест

Дата: 2026-11-21
Сервер: `192.168.1.233:8443`, Docker Compose, Debian 13, 2 vCPU, 2 ГиБ RAM.

## Найденные баги и что исправлено

### 1. Скачанный сейф не появлялся в открытом приложении

Синхронизация заменяла файл в кэше, но открытая сессия продолжала держать старое
`VaultData` в памяти: новые записи появлялись только после перезапуска. Даже кнопка
«Синхронизировать сейчас» обновляла файл, а не экран.

Исправлено: команда `vault_reload` перечитывает файл в **ту же** сессию ключом из
сессии (мастер-ключ не нужен), движок синхронизации вызывает её сразу после успешного
`pull`, стор подменяет `data`. Тесты: `reload_tests` (Rust), `reloadFromDisk` и
`onPulled` (TS).

### 2. Приложение «выкидывало с сервера» без причины

Сессия сервера живёт только в памяти Rust, а сервер держит не больше N сессий на
аккаунт: при входе с другого устройства самая старая вытесняется. Телефон получал
`remote_unauthorized` и до перезапуска не синхронизировался.

Исправлено:
- клиент при `needs-auth` сам пробует `remote_refresh` сохранённым семенем ключа —
  вытесненная сессия восстанавливается без ввода пароля;
- если семени нет (сейф заблокирован), синхронизация замолкает, показывает
  «Требуется вход на сервер» и кнопку «Войти заново», сеть не дёргает;
- после разблокировки сейфа вход выполняется автоматически (мастер-пароль или биометрия);
- предел сессий на аккаунт поднят с 5 до 10: переустановка приложения при отладке больше
  не выбивает телефон.

### 3. Конфиг сервера нельзя было править без пересборки образа

`server.toml` копировался в образ. Теперь он монтируется из `deploy/docker/server.toml`
только на чтение: правка квот и лимитов — рестарт контейнера.

## Нагрузочный тест

Инструмент: `cargo run -p pms-server --release --example loadtest -- \
  --url https://… --users 200 --pushes 50 --concurrency 32`.
Регистрация, вход по логину и 50 сохранений на пользователя (тело 2 КБ, `If-Match`).

### Замеры

| Показатель | Простой | Пик нагрузки | После теста |
|---|---|---|---|
| CPU контейнера (cgroup) | 0 % | **≈ 126 % одного ядра** (3.38 с CPU за 2.67 с) | 0 % |
| CPU хоста (2 ядра) | 11–15 % | **пик 84 %** | 11 % |
| Память контейнера (`memory.current`) | 7.6 МиБ | **пик 34.8 МиБ** | 33.0 МиБ |
| Память хоста (занято) | 447 МиБ | 448 МиБ | 448 МиБ |
| Swap | 42 МиБ | — | 42 МиБ |

Лимит контейнера — 256 МиБ: запас почти восьмикратный.

### Пропускная способность

| Операция | Результат |
|---|---|
| Регистрация + вход | 200 аккаунтов за 249 мс (803/с), ошибок 0 |
| Сохранение сейфа (2 КБ) | 10 000 запросов за 2 284 мс (**4 378/с**), ошибок 0 |
| Задержка `PUT /v1/vault` | p50 6 мс · p95 11 мс · p99 16 мс · max 25 мс |
| CPU на один `PUT` | ≈ 0.34 мс (включая TLS, BLAKE3, `fsync`, SQLite) |

После теста на сервере 720 аккаунтов (все прогоны вместе), 14 МБ данных, `healthz` 200,
все процессы живы. Память после нагрузки не возвращается к 7.6 МиБ, а остаётся около
33 МиБ: это аллокатор и страницы SQLite, а не утечка — сервер под нагрузкой держит
примерно те же 35 МиБ.

## Что это значит для целевой VM

Один аккаунт человека — это единичные сохранения в минуту. Запас, замеренный выше,
покрывает тысячи пользователей на одном 2-ядерном VPS; узким местом раньше был лимит
регистраций (30/мин по умолчанию), а не процессор или память.

## Аллокации и реаллокации (постоянный режим, без сети и TLS)

`cargo run -p pms-server --release --example allocbench` — запросы идут прямо в
роутер, счётчик считает глобальный аллокатор (mimalloc). Три прогрева, затем
усреднение по 20 запросам (healthz — по 50).

| Запрос | alloc | realloc | байт |
|---|---|---|---|
| `POST /v1/accounts` (пустой сейф) | 115 | 17 | 81 КБ |
| `POST /v1/auth/challenge` | 84 | 6 | 8.4 КБ |
| `POST /v1/auth/verify` | 108 | 12 | 9.7 КБ |
| `PUT /v1/vault` 2 КиБ | **96** | **10** | 79 КБ |
| `PUT /v1/vault` 64 КиБ | 96 | 10 | 141 КБ |
| `PUT /v1/vault` 1 МиБ | 111 | 10 | 145 КБ |
| `GET /v1/vault` (без чтения тела) | 71 | 8 | 72 КБ |
| `GET /v1/healthz` | 24 | 0 | 2.7 КБ |
| `Store::put_vault` 64 КиБ (без HTTP) | 32 | 6 | 67 КБ |

Что это значит:

- **Аллокации не зависят от размера**: 96 аллокаций и 10 реаллокаций и для 2 КиБ, и
  для 1 МиБ. Рабочий набор — один буфер 64 КиБ: байты растут на 62 КБ между 2 КиБ и
  1 МиБ и дальше не растут. Тело никогда не буферизуется целиком.
- **Реаллокаций ровно 10 на запись** (SQLite-страницы и строка ответа), и их число
  не меняется с размером. Для сравнения, до правок чтение 1 МиБ давало 843
  аллокации и 3.2 МБ — из-за кусков по 8 КиБ и буферизации; теперь 71 и 72 КБ.
- Что осталось: 96 аллокаций — это стоимость стека hyper/axum (карты заголовков,
  тело запроса, канал задачи) плюс JSON-ответ и подготовка SQLite. Собственный код
  хранилища — 32 аллокации, из них 6 реаллокаций. Ниже без смены HTTP-стека не
  уйти; **байты на запись уже константны и не зависят от payload** — это и есть
  практическое «близко к нулю» для сетевого сервера.

Внесённые по ходу правки: `prepare_cached` для горячих запросов, одна hex-строка
аккаунта на запрос вместо трёх, тело `/v1/healthz` собирается один раз (24
аллокации против 29), отдача файлов куском 64 КиБ вместо 8 КиБ.

## SIMD

Своих SIMD-ядер в коде нет, и они не нужны: вся векторизация приходит из библиотек.

- TLS (`aws-lc-rs`): на процессоре VM есть `aes`, `avx2`, `sha_ni` — рукопожатие и
  AES-GCM идут по AES-NI/AVX2, SHA — по аппаратным расширениям. На 2 ядрах это даёт
  полный гигабит без заметной доли CPU: при 4.6 тыс. запросов/с сервер тратит
  1.45 ядра, из которых большая часть — сеть и SQLite, а не шифрование.
- `blake3`: SIMD-путь (AVX2) включается на крупных входах; для сейфа в единицы
  килобайт выгоды нет, для вложений в мегабайты — есть.
- Наш горячий цикл (копирование 64 КиБ кусками) — это `memcpy` и `write`, их
  векторизует компилятор и libc.

Итог: на этом CPU добавление ручных SIMD-инструкций ничего не даст — узкое место
не в арифметике.

## Параллелизм и предел

Токены: tokio с числом воркеров по числу ядер (2), запись в один аккаунт
сериализуется мьютексом аккаунта, разные аккаунты идут параллельно.

Нагрузка: `--users N --duration 8 --concurrency C`, каждый пользователь пишет свой
сейф (2 КиБ), `If-Match` по версии.

| Параллельно | Запросов/с | p50, мс | p95, мс | p99, мс | CPU контейнера | Память, пик |
|---|---|---|---|---|---|---|
| 8 | 3 312 | 2 | 3 | 5 | 102 % ядра | 32 МиБ |
| **32** | **4 653** | **6** | **10** | **13** | **146 %** | **40 МиБ** |
| 64 | 4 516 | 13 | 21 | 27 | 145 % | 53 МиБ |
| 128 | 4 328 | 28 | 46 | 60 | 145 % | 86 МиБ |
| 256 | 4 046 | 60 | 106 | 133 | 140 % | 134 МиБ |
| 512 | 4 211 | 122 | 167 | 187 | 145 % | **208 МиБ** |

Колено — **32 одновременных запроса**: дальше пропускная способность стоит на
4.2–4.6 тыс./с, а растут только задержка и память (~330 КБ на запрос в полёте).

Устойчивость (60 секунд при параллелизме 32, без перезапусков):

| Показатель | Значение |
|---|---|
| Сохранений | **277 253 за 60 с = 4 620/с**, ошибок 0 |
| Задержка | p50 6 мс · p95 10 мс · p99 13 мс · max 29 мс |
| CPU | 149 % одного ядра (≈1.5 из 2), хост — 90 % |
| Память | пик 120 МиБ, к концу 92 МиБ (не растёт) |
| Запись на диск | 1.15 ГБ за минуту ≈ 19 МБ/с, ≈ 4.2 КБ на запрос (сейф + WAL) |

Выводы о пределе:

- **Предел этого VPS — примерно 4.6 тыс. сохранений в секунду** и он упирается не в
  память и не в криптографию, а в связку «два ядра + fsync на каждый PUT + сетевой
  стек хоста»: контейнер занимает 1.45 ядра из 2, хост при этом загружен на 90 %.
- Держать такую нагрузку можно **неограниченно долго**: за минуту непрерывной работы
  ни ошибок, ни роста памяти, ни деградации задержки.
- По памяти в лимит 256 МиБ сервер упирается при ~600–700 одновременных запросах в
  полёте; при 512 в полёте пик 208 МиБ. Для человека с телефоном и ноутбуком это
  недостижимо, но если ставить лимит меньше, надо помнить про ~330 КБ на запрос.
- Один аккаунт пишет через мьютекс: два устройства одного человека сериализуются, и
  это правильно (конфликт версий дешевле, чем потеря записи). Тысячи пользователей
  друг другу не мешают.

## Закалка: что сделано и что изменилось в цифрах

Дата: 2026-11-22. План: `docs/superpowers/plans/2026-11-22-server-hardening.md`.
Вердикты: `docs/reports/2026-11-22-server-review-verdicts.md`.

### Сделано

- **P0.1 Дедлайны**: header-read и first-request таймауты на листенере,
  общий бюджет на приём тела (база + минимум 512 КиБ/с), JSON-тела с дедлайном.
  Тесты `tests/timeouts.rs` (недописанные заголовки и «тело не приходит»).
- **P0.2 Nonce**: индекс по `expires_at`, один активный nonce на аккаунт, чистка
  каждые 64 вставки; лимитер на `challenge` теперь под ключом аккаунта (раньше не
  работал вовсе).
- **P0.3 Сессии**: индекс по `expires_at`, вытеснение по порядку вставки,
  чистка раз в минуту при обращении, новый `POST /v1/auth/session/revoke`.
- **P0.4 Удаление аккаунта**: под мьютексом аккаунта, при неудаче удаления файлов
  строки индекса не трогаются; подпись удаления привязана ко времени
  (`x-pms-timestamp`, окно ±120 с) и не может быть повторена (`last_delete_at`).
- **P0.5 Диск и память**: бюджет `staging/` (резерв до записи, четверть свободного
  места, 64 МиБ…8 ГиБ), освобождение в `Drop` даже при отмене; `max_connections`
  128 по умолчанию; `ulimits.nofile 8192`, `stop_grace_period: 30s`, лимит памяти
  контейнера 384 МиБ.
- **P0.6 Оракул логина**: неизвестный логин получает такой же nonce, различие
  только на `verify` (единый 401); внутренний текст ошибки больше не уходит наружу.
- **P1.2 fsync**: политика `always | data | batch`; `data` — `sync_data`, `batch` —
  фон сбрасывает раз в 3 мс. В контейнере включён `batch`.
- **P1.5 частично**: буфер по размеру тела, проверка версии протокола без `String`.
- **P2.1/P2.3**: `recount` пересчитывает дайджест по файлу, если размер разошёлся
  (клиент снова может скачать сейф после сбоя); на старте чистится `staging/`;
  SIGTERM обрабатывается наравне с `ctrl+C`.

### Второй заход (2026-11-22)

Сделано дополнительно:

- **P1.1 частично**: `session()` через `prepare_cached`; проверка токена уведена с
  воркеров tokio в `spawn_blocking` — самый частый запрос в SQLite больше не держит
  реактор.
- **P1.4**: повторная загрузка блоба возвращает данные из одного чтения (было до
  трёх), а отметка использования обновляется не чаще раза в час — скачивание
  вложений больше не пишет в WAL на каждый GET/HEAD.
- **P2.1**: `recount` пересчитывает дайджест по файлу, если размер разошёлся —
  после сбоя клиент снова может скачать сейф (было: навсегда «BLAKE3 не совпал»).
- **P2.3**: `staging/` чистится на старте, SIGTERM обрабатывается.

Замер после второго захода (C=32, 10 с, `fsync=batch`): **5 725 PUT/s**, p50 5 мс,
p99 12 мс, 0 ошибок, CPU 155 % ядра. Это в пределах разброса с первым замером
(5 996) — правки P1.1/P1.4 бьют по путям аутентификации и чтения, а не по записи.

### Третий заход (2026-11-22, завершение плана)

- **P1.1**: пул соединений только для чтения (`with_read`, до 4 соединений, `query_only`),
  читатели больше не ждут писателя; `session()`, `account()`, `blob_info()`, `list_blobs()`,
  `usage()` переведены на пул; проверка токена уведена в `spawn_blocking`.
- **P1.3**: регистрация с сейфом — один проход: `put_vault_from_staged` переименовывает
  уже принятый файл и берёт готовый BLAKE3 (раньше: две записи, два хеша, два fsync).
- **P1.5**: TLS-тикеты сессии (возобновление без полного рукопожатия), карта блокировок
  аккаунта чистится при удалении.
- **P2.2**: `recount` удаляет осиротевшие файлы блобов и считает квоту только по файлам
  со строкой в индексе (раньше мусор от сбоя занимал квоту).
- **P2.4**: `backup.sh` снимает данные **до** индекса — при восстановлении `recount`
  поправит дайджест по файлу.

Замеры после третьего захода (та же VM):

| Сценарий | Результат |
|---|---|
| Запись, C=32, 10 с | **5 798 PUT/s**, p50 5 мс, p99 12 мс, CPU 161 % ядра |
| Чтение, C=32, 8 с | **12 746 GET/s**, p50 2 мс, p99 4 мс, 0 ошибок |
| Регистрация | 715 аккаунтов/с (было 369–805, зависит от прогрева) |

Итог к базовой линии: запись **+25 %** (4 653 → 5 798), чтение не изменилось
(12.7k/s и раньше — оно упирается в CPU/TLS, а не в SQLite). Выигрыш пула чтения —
не в одиночном GET, а в отсутствии конкуренции с писателем под смешанной нагрузкой.
