# Синхронизация: три бага с устройства и нагрузочный тест

Дата: 2026-11-21
Сервер: `192.168.1.233:8443`, Docker Compose, Debian 13, 2 vCPU, 2 ГиБ RAM.

## Найденные баги и что исправлено

### 1. Скачанный сейф не появлялся в открытом приложении

Синхронизация заменяла файл в кэше, но открытая сессия продолжала держать старое
`VaultData` в памяти: новые записи появлялись только после перезапуска. Даже кнопка
«Синхронизировать сейчас» обновляла файл, а не экран.

Исправлено: команда `vault_reload` перечитывает файл в **ту же** сессию ключом из
сессии (мастер-ключ не нужен), движок синхронизации вызывает её сразу после успешного
`pull`, стор подменяет `data`. Тесты: `reload_tests` (Rust), `reloadFromDisk` и
`onPulled` (TS).

### 2. Приложение «выкидывало с сервера» без причины

Сессия сервера живёт только в памяти Rust, а сервер держит не больше N сессий на
аккаунт: при входе с другого устройства самая старая вытесняется. Телефон получал
`remote_unauthorized` и до перезапуска не синхронизировался.

Исправлено:
- клиент при `needs-auth` сам пробует `remote_refresh` сохранённым семенем ключа —
  вытесненная сессия восстанавливается без ввода пароля;
- если семени нет (сейф заблокирован), синхронизация замолкает, показывает
  «Требуется вход на сервер» и кнопку «Войти заново», сеть не дёргает;
- после разблокировки сейфа вход выполняется автоматически (мастер-пароль или биометрия);
- предел сессий на аккаунт поднят с 5 до 10: переустановка приложения при отладке больше
  не выбивает телефон.

### 3. Конфиг сервера нельзя было править без пересборки образа

`server.toml` копировался в образ. Теперь он монтируется из `deploy/docker/server.toml`
только на чтение: правка квот и лимитов — рестарт контейнера.

## Нагрузочный тест

Инструмент: `cargo run -p pms-server --release --example loadtest -- \
  --url https://… --users 200 --pushes 50 --concurrency 32`.
Регистрация, вход по логину и 50 сохранений на пользователя (тело 2 КБ, `If-Match`).

### Замеры

| Показатель | Простой | Пик нагрузки | После теста |
|---|---|---|---|
| CPU контейнера (cgroup) | 0 % | **≈ 126 % одного ядра** (3.38 с CPU за 2.67 с) | 0 % |
| CPU хоста (2 ядра) | 11–15 % | **пик 84 %** | 11 % |
| Память контейнера (`memory.current`) | 7.6 МиБ | **пик 34.8 МиБ** | 33.0 МиБ |
| Память хоста (занято) | 447 МиБ | 448 МиБ | 448 МиБ |
| Swap | 42 МиБ | — | 42 МиБ |

Лимит контейнера — 256 МиБ: запас почти восьмикратный.

### Пропускная способность

| Операция | Результат |
|---|---|
| Регистрация + вход | 200 аккаунтов за 249 мс (803/с), ошибок 0 |
| Сохранение сейфа (2 КБ) | 10 000 запросов за 2 284 мс (**4 378/с**), ошибок 0 |
| Задержка `PUT /v1/vault` | p50 6 мс · p95 11 мс · p99 16 мс · max 25 мс |
| CPU на один `PUT` | ≈ 0.34 мс (включая TLS, BLAKE3, `fsync`, SQLite) |

После теста на сервере 720 аккаунтов (все прогоны вместе), 14 МБ данных, `healthz` 200,
все процессы живы. Память после нагрузки не возвращается к 7.6 МиБ, а остаётся около
33 МиБ: это аллокатор и страницы SQLite, а не утечка — сервер под нагрузкой держит
примерно те же 35 МиБ.

## Что это значит для целевой VM

Один аккаунт человека — это единичные сохранения в минуту. Запас, замеренный выше,
покрывает тысячи пользователей на одном 2-ядерном VPS; узким местом раньше был лимит
регистраций (30/мин по умолчанию), а не процессор или память.
