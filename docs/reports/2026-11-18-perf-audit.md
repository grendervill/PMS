## 3. Находки

### PERF-01 · High · Двойной base64 вокруг каждого сохранения и вложения

Сквозной путь сейчас (desktop):

```
Rust: JSON → AEAD → файл(Vec) → base64 (String)
IPC  ─────────────────────────────────────────────► JS: atob + побайтовый цикл → Uint8Array
JS:   createBackup?  → Uint8Array → btoa
IPC  ◄───────────────────────────────────────────── Rust: base64 decode → Vec<u8> → atomic write
```

* `src/features/vault/api.ts:228-234` (`save` → `fromBase64`), `src/lib/storage/desktop.ts:76-82` (`writeVault` → `toBase64`), команда `commands/storage.rs:108-116`.
* Вложения: `api.ts:257-283` (`sealAttachment`/`openAttachment`) + `writeBlob`/`readBlob` → **3 roundtrip'а** на загрузку 10-мегабайтного файла ≈ 0.5 с чистого JS-копирования.
* Цена: 69 мс и +18.5 МБ heap на каждые 4 МиБ (2.5), плюс 33 % раздувание объёма на проводе и два лишних полных буфера.

**Как убрать.** В Tauri 2 есть raw-IPC: фронт вызывает `invoke("…", new Uint8Array(...))`, Rust принимает `tauri::ipc::Request<'_>` (`InvokeBody::Raw`), а возвращает `tauri::ipc::Response::new(Vec<u8>)` → в JS приходит `ArrayBuffer` (`tauri-2.12.4/src/ipc/mod.rs:59-64`; в `@tauri-apps/api` `InvokeArgs = … | Uint8Array`). Для сохранения можно убрать и второй hop: писать файл из Rust (`vault_save_to(session_id, data, folder)`), тогда байты вообще не ездят в JS.

```rust
#[tauri::command]
pub fn vault_save(session_id: Uuid, data: VaultData, state: State<'_, AppState>)
    -> ApiResult<tauri::ipc::Response>            // ArrayBuffer на фронте
```
```ts
const file = new Uint8Array(await invoke("vault_save", { sessionId, data }));   // 0 base64
```
Ограничение: на Android raw-запрос **не поддерживается** (`tauri-2.12.4/src/ipc/mod.rs:55` — «на Android `InvokeBody` всегда `Json`»), там нужен прежний base64-путь; ответ (`Response`) работает везде. Проверять платформу в одном месте (`vaultApi`), чтобы не размазывать `if (isAndroid)`.

**Ожидаемый эффект:** −100 % JS-копирования на desktop; −33 % объёма IPC; −2 буфера на операцию. Для 4 МиБ: 148 мс → 6 мс (см. 2.4+2.5).

**Приёмка:** e2e-тест, что `vault_save` отдаёт `ArrayBuffer` на desktop и строку на Android; сохранение 4 МиБ ≤ 10 мс на Rust-стороне; отсутствие `toBase64` в пути `save` (grep-тест в CI).

### PERF-02 · High · Пять полных проходов по телу хранилища при сохранении

`core/crypto.rs:155-231` + `core/vault.rs:145-163,248-253` + `core/vault_file.rs:70-88`:

1. `serde_json::to_vec(data)` — буфер JSON (растёт реаллокациями);
2. `seal_payload` → `cipher.encrypt(...)` — аллокация шифротекста (копия №2);
3. `seal_payload` → `envelope` с `salt`+`nonce`+ct (`extend_from_slice`) — копия №3;
4. `serialize_file` → `payload.to_vec()` (поле `VaultFile.payload: Vec<u8>`) — копия №4;
5. `serialize_vault_file` → `bytes.extend_from_slice(&file.payload)` — копия №5;
6. `STANDARD.encode` — 1.33× буфер + ещё одна копия (см. PERF-01).

Замер 2.4: **6 аллокаций, 21.8 МиБ выделено, пик 17.7 МиБ на 4 МиБ данных**, 8.67 мс.

**Как убрать.** Один буфер на всё: заранее зарезервировать место под заголовок, писать JSON прямо в него, шифровать **на месте**, длину записать после.

```rust
// core/vault.rs
pub fn seal_vault_in_place(session: &mut VaultSession, data: &VaultData) -> Result<Vec<u8>, VaultError> {
    let mut buf = Vec::with_capacity(17 + HEADER_RESERVE + estimate + 1 + 32 + 24 + 16);
    buf.resize(17 + HEADER_RESERVE, 0);              // место под magic+lengths+JSON
    serde_json::to_writer(&mut buf, data)?;          // без промежуточного Vec
    let ct_start = 17 + HEADER_RESERVE;
    // salt|nonce уже лежат в buf, либо пишутся перед ct
    let tag = cipher.encrypt_in_place_detached(nonce, aad, &mut buf[ct_start + 56..])?;
    buf.extend_from_slice(&tag);
    // …записать header_json в зарезервированную область (или offset-таблицу), magic, длины
}
```
Плюс `serialize_vault_file(header, payload: &[u8])` вместо `payload.to_vec()` (убрать копию №4) и `random_array::<24>()` вместо `random_bytes(cipher.nonce_len())` (`crypto.rs:163, 549-557`).

**Ожидаемый эффект:** 6 → 1 аллокация, 21.8 → 4.1 МиБ выделено, пик 17.7 → 4.1 МиБ, 8.67 → 5.88 мс (**−83 % байт, −77 % пика, −32 % времени**). На Android (мало RAM) это важнее, чем на десктопе.

**Приёмка:** `save_path_probe` (возвращён в `perf_audit.rs` как постоянный тест) фиксирует `alloc ≤ 2`, `peak ≤ 1.1 × plaintext`, и сравнивает байты файла с текущей реализацией побайтово.

### PERF-03 · Medium · `rewrap` и `remove_slot` копируют всё тело ради нового заголовка

`core/vault.rs:165-224` → `serialize_file(&header, &session.payload)` → `payload.to_vec()` + сборка. Для хранилища 100 МиБ смена парольной фразы делает лишние 200 МиБ копий и пик +200 МиБ.

**Как убрать:** функция, которая отдаёт `(header_json, &[u8])` и пишется на диск потоком (`File::create` + `write_all(header)` + `write_all(&payload)` + `sync_all`), без сборки `Vec` целиком. Заодно это делает rewrap O(1) по памяти.

### PERF-04 · Medium‑High · Экспорт/импорт архива держит в RAM весь архив

`core/pms_archive.rs:62-123` — `files: Vec<(String, Vec<u8>)>` со **всем** хранилищем и **всеми** вложениями, плюс отдельный проход SHA-256, плюс `Manifest` со всеми путями. Пик ≈ 2× размера архива; при `MAX_UNPACKED = 2 ГиБ` это до 4 ГиБ.

`import` (`:187-215`) читает каждый файл в `Vec` (`with_capacity(entry.size() as usize)` — по недоверенному значению), сверяет SHA-256 и пишет. Плюс `commands/transfer.rs:554` (send) отправляет архив целиком через `std::io::copy` — это уже потоково (ок).

**Как убрать:** потоковый экспорт — манифест первым (`Stored`, размеры известны), затем по одному файлу: открыть, посчитать SHA-256 в первом проходе ИЛИ писать манифест последним (порядок записей в zip не важен для чтения); буфер 1 МиБ. Импорт — так же: `io::copy` из `entry` в файл с параллельным хешированием (`sha2` умеет `update`), без накопления.

**Эффект:** пик памяти с 2× размера архива до ~2 МиБ постоянно; заодно закрывает SEC-04 (бюджет становится естественным).

### PERF-05 · High · Синхронные команды выполняются на главном потоке

`tauri-2.12.4/src/manager/mod.rs:458-459` — `run_invoke_handler` вызывает зарегистрированный обработчик **синхронно** в том потоке, откуда пришло IPC-сообщение (на macOS это поток WKScriptMessageHandler, т.е. главный; на Windows — UI-поток WebView2). Значит любая `fn` без `async` блокирует отрисовку.

Сейчас на главном потоке: `vault_unlock` (Argon2id 65–512 МиБ, ~0.3–1.5 с), `vault_save` (PERF-02), `vault_create`, `attachment_seal/open` (до 100 МиБ), `import_parse` (до 500 МБ), `pms_export/pms_import`, `ssh_formats` (RSA — секунды), `totp_code` (мелочь, но раз в секунду на запись). Уже правильно сделано в `ssh_generate`, `transfer_scan`, `transfer_send`, `transfer_install` — `spawn_blocking`.

**Побочный эффект:** ввод и любые rAF-анимации (`motion`/framer) замирают на всё время операции; часть CSS-анимаций может продолжаться на композиторе, но реакция на клики/набор — нет.

**Как убрать:**
```rust
#[tauri::command]
pub async fn vault_unlock(...) -> ApiResult<UnlockVaultResponse> {
    let file = decode(file_b64)?;               // дёшево, на IPC-потоке
    tauri::async_runtime::spawn_blocking(move || unlock_vault(&file, &secret))
        .await
        .map_err(|e| ApiError::new("unlock", e.to_string()))?
}
```
Для долгих операций (импорт, экспорт) — `Channel`/события прогресса, чтобы UI показывал процент.

**Приёмка:** при `vault_unlock` с профилем Paranoid (512 МиБ) анимация в UI продолжается (e2e: `requestAnimationFrame` счётчик > 30 кадров за время операции); `cargo test` не меняется.

### PERF-06 · Medium · Мьютекс сессии сериализует все команды

`core/session.rs:31-61` — `with`/`with_mut` держат `Mutex<Option<VaultSession>>` на время замыкания; в `vault_save` это вся крипто-работа, в `attachment_seal` — AEAD до 100 МиБ, в `attachment_open` — тоже. Пока идёт одна операция, `vault_lock`, чтение списка вложений и сохранение ждут (и блокируют главный поток, PERF-05).

**Как убрать:** `SessionManager::key(id) -> Zeroizing<[u8; 32]>` + `vault_id()` (копия 32 байт под мьютексом), работа вне мьютекса, `set_payload()` — короткое обновление. После этого несколько вложений можно шифровать параллельно (PERF-09).

### PERF-07 · Medium · AES-256-GCM на ARM в 3.3 раза медленнее возможного

Замер: XChaCha **617 МиБ/с**, AES-256-GCM **184 МиБ/с**. Причина — `aes 0.8.4` включает ARMv8-intrinsics только при `--cfg aes_armv8` (`aes-0.8.4/src/lib.rs:134`), иначе используется «soft» (fixsliced) реализация. Важно: при включённом cfg применяется **runtime-детект** через `cpufeatures::new!(aes_intrinsics, "aes")` (`aes-0.8.4/src/autodetect.rs:23`) — на ядрах без крипто-расширений автоматически soft-путь, падения «незаконная инструкция» не будет.

**Как убрать:**
```toml
# src-tauri/.cargo/config.toml
[target.aarch64-apple-darwin]
rustflags = ["--cfg", "aes_armv8"]
[target.aarch64-apple-ios]
rustflags = ["--cfg", "aes_armv8"]
[target.aarch64-linux-android]
rustflags = ["--cfg", "aes_armv8"]
[target.aarch64-unknown-linux-gnu]
rustflags = ["--cfg", "aes_armv8"]
```
Ожидаемо ≈ 890 МиБ/с (число из прошлого отчёта) — AES-256-GCM перестаёт быть «медленным выбором». Проверить в `perf_audit` на всех целевых платформах (x86_64 уже использует AES-NI автоматически).

### PERF-08 · SIMD: что делать **не** надо

Замеры показывают, что узкое место — не арифметика:

* `base64` (скалярный крейт) — **3 973 МиБ/с**; это уже скорость памяти, `base64-simd` не даст ничего, кроме новой зависимости и `unsafe`.
* SHA-256 — **544 МиБ/с**; расширение SHA2 на aarch64 определяется автоматически (`sha2` 0.10).
* ChaCha20-Poly1305 — **617 МиБ/с**; AVX2/NEON-бэкенды в `chacha20poly1305` включаются `cpufeatures` сами.

Реальные SIMD-задачи: (1) AES на aarch64 (PERF-07); (2) опционально `flate2` c `zlib-ng` для распаковки 1PUX (сейчас `miniz_oxide`, нужно только на импорте 1PUX); (3) `jsQR` — не SIMD, а вынос из главного потока (PERF-11).

### PERF-09 · Medium · Параллелизм не используется — но не везде он полезен

Замер «потолка» (2.3): импорт 1.79×/2.66×, seal 3.66×. Но важно: в стенде импорт режется на **4 независимых JSON-документа**. Реальный файл — один JSON; чтобы получить выигрыш, нужно предварительно разрезать массив `items` по границам объектов и парсить чанки независимо. Это усложняет парсер (`Cow`-строки, порядок, предупреждения) и повышает риск ошибок — **не рекомендую** для импорта.

Где параллелизм даёт выигрыш без риска:

| Место | Что делать | Ожидаемо |
|---|---|---|
| Вложения при экспорте/пересылке (`pms_archive::export`, `stageVaultForTransfer`) | пул на `available_parallelism()` потоков: SHA-256 + запись независимых файлов | 2–3.5× на 4+ файлах |
| Шифрование/расшифровка нескольких вложений (`attachment_seal/open` батчем) | то же, после PERF-06 | до 3.6× (замер seal) |
| Favicon'ы | Rust-команда `favicon_fetch_many(hosts)` с семафором 4–6 | вместо N последовательных IPC |
| Проверка целостности хранилища / отпечатки | SHA-256 в 2–4 потока по диапазонам | ~2–3× (544 МиБ/с × N) |
| `jsQR` | Worker (Main-поток свободен) | −10…20 мс/кадр |

Реализация: `rayon` (`par_iter`) либо `std::thread::scope` (как уже сделано в стенде, без новой зависимости). Для менеджера паролей предпочтительнее **scope** — меньше поверхности (нет глобального пула).

### PERF-10 · Medium · Кэш favicon'ов: O(n²) и квота localStorage

`src/features/entries/faviconCache.ts:80-87,103-116` — `persist()` вызывает `JSON.stringify` **всей** карты (до 300 записей, каждая data-URL до ~20 КБ) при **каждом** новом значке; `remember()` дополнительно `Object.keys` + сдвиг. Итого O(n²) работы и несколько МБ строк каждые несколько секунд при прокрутке списка; квота localStorage (5 МБ) ловится исключением и глотается — кэш молча перестаёт сохраняться.

**Как убрать:** IndexedDB (одна запись на хост, ключ `host`), либо `localStorage` с ключом на хост (`pms.fav1.<host>`), плюс пакетная очистка раз в N записей. Писать только изменённый ключ.

### PERF-11 · Medium · Сканер QR на главном потоке

`src/features/qr/QrScannerDialog.tsx:72-109` — в цикле `requestAnimationFrame`: `drawImage` + `getImageData` (полный кадр камеры, 1280×720 → 3.7 МБ на кадр) + `jsQR`. Это 10–20 мс на кадр и постоянный GC-шум; на телефоне — заметный нагрев и просадка FPS.

**Как убрать:** `BarcodeDetector` где доступен; иначе `Worker` + `OffscreenCanvas`, кадр раз в 100–150 мс, даунсемпл до 640 px по длинной стороне (QR читается), `willReadFrequently: true` для 2d-контекста.

### PERF-12 · Medium · Нет виртуализации списка записей

`src/features/entries/EntryList.tsx:103` — `entries.map(...)` без windowing; `EntriesView.tsx:88-91` сортирует/фильтрует на каждый ввод (в `useMemo`, но O(n log n)). Импорт на 20 000 записей (сценарий, который проект сам же и тестирует в `perf_audit`) даёт 20 000 смонтированных `EntryCard` + 20 000 эффектов загрузки favicon.

**Как убрать:** виртуализация (`@tanstack/react-virtual`, ~1 КБ + 2 обёртки) или простой windowing по `scrollTop`; порог — включать при `entries.length > 200`.

### PERF-13 · Low · Мелкие аллокации в горячем пути ядра

* `core/crypto.rs:163` — `random_bytes(cipher.nonce_len())` → `Vec` на 24 байта на каждый `seal_payload` (можно `[u8; 24]`, `fn random_bytes` — строка 549).
* `core/crypto.rs:249-258, 260-273` — `header_core_aad`/`slot_aad` собирают `Vec` на каждый сейв/слот.
* `core/vault.rs:248-253` — `serialize_file` клонирует заголовок и `payload.to_vec()` (см. PERF-02).

По отдельности это копейки, но они в пути, который вызывается на каждое сохранение; убираются заодно с PERF-02.

### PERF-14 · Low · Сохранение на каждое изменение + фоновые list_dir

`src/features/vault/store.ts:330-345` — `save()` вызывается на каждое действие (`addEntry`, `updateEntry`, …), и каждый раз: `createBackup` → `listBackups` (чтение каталога + IPC), затем полный `VaultData` в JSON через IPC, затем запись. `listBackups` при этом нужен только чтобы понять, не пора ли делать бэкап.

**Как убрать:** кэш «последний бэкап» в модуле (инвалидировать после `writeBackup`); дебаунс 150–300 мс для текстовых правок (черновик и так есть — `draftRegistry`); для больших хранилищ — сохранять по `Ctrl+S`/blur, а не на каждый символ.

---

### PERF-15 · Low · `VaultSession.payload` — копия шифротекста на всю сессию

`core/vault.rs:23-28` — после `unlock` в памяти лежит `payload` (шифротекст), он нужен только `rewrap`/`remove_slot`. Для хранилища 2 ГиБ это +2 ГиБ RSS всё время работы.

**Как убрать:** не хранить `payload`; для `rewrap` пересобрать файл из ciphertext на диске (перечитать `pms.vault`), либо хранить только `header` и путь. Альтернатива — оставить как есть и задокументировать (rewrap без чтения диска быстрее, а типичный vault — единицы МБ).

### PERF-16 · Info · Импорт трогать не надо

7 аллокаций на запись, 0 реаллокаций на запись, 35 МБ пика на 20 000 записей, 57 мс. Остаток (`uris`, `fields`, `passwordHistory`, выходные `urls`/`password_history`, комментарий, TOTP) убирается кастомными десериализаторами массивов (−3/запись), но выигрыш — единицы процентов при реальных объёмах. Не приоритет.

* `VaultSession.payload` (PERF-15) — оставить, если не появятся хранилища в гигабайты; иначе вернуться к пункту 10.
