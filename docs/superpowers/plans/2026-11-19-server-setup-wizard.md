# PMS Server — План 7: логин и мастер настройки сервера

**Статус:** логин (задачи 1–3) **реализован 2026-11-20**; мастер настройки (задачи 4–7)
запланирован. Зафиксировано по просьбе пользователя 2026-11-19, с уточнением: SSL
настраивается при развёртывании сервера, а не в приложении.
**Спека:** `docs/superpowers/specs/2026-11-18-server-sync-design.md` §18.
**Связанные планы:** `-06-docker.md` (развёртывание и сертификаты), `-03-storage-mode.md` (форма профиля).

## Что просит пользователь

1. Сервер один, пользователей много. Вход — **логин + мастер-пароль** (или биометрия);
   верная пара открывает хранилище именно этого пользователя. Логин **сохраняется** в
   приложении, чтобы его не вводить каждый раз.
2. При выборе серверного режима первым шагом идёт **настройка сервера**, которую можно
   **пропустить**, если сервер уже есть (тогда сразу URL + логин + мастер-пароль).
3. **SSL-сертификат настраивается при развёртывании на сервере**, там же выбирается
   вариант: **самоподписанный на 10 лет** или **Let's Encrypt**; оба — с автопродлением
   (Caddy для ACME, cron для самоподписанного). Приложение сертификаты не выпускает,
   оно проверяет сервер и запоминает отпечаток.

## Что это меняет в уже сделанном

| Сейчас | Станет |
|---|---|
| `account_id = BLAKE3(Ed25519-ключ из мастер-ключа)`, логина нет | соль identity-ключа включает логин: `HKDF(master, "PMS-IDENTITY-SALT-v1" ‖ login)`; аккаунт = пара (логин, мастер-пароль) |
| `POST /v1/auth/challenge {account_id, device_id}` | `{login, device_id}`; сервер сам находит аккаунт по логину |
| `POST /v1/accounts` без логина | `{login, …}`, уникальность логина, `409 login_taken` |
| профиль: `{id, name, baseUrl, accountId, tls, lastLoginAt}` | плюс `login` |
| форма: URL → проверка → мастер-ключ | URL → (настройка сервера, можно пропустить) → проверка → логин + мастер-ключ |
| сервер: аккаунт по `account_id` | таблица `logins(login UNIQUE, account_id)` + прежний `account_id` как ключ данных |

## Задачи (по порядку; каждая меняет протокол, поэтому первая — дизайн)

1. ✅ **Дизайн-решение по §18.** Ответить на открытые вопросы: админ-доступ и квоты (CLI или
   пароль), смена логина (перенос аккаунта или фикс навсегда), токен регистрации в
   мастере, несколько профилей на устройстве, поведение при смене сертификата.
   Обновить §7 и §9 спеки под логин, затем код.
2. ✅ **Протокол.** `identity_salt` с логином; `challenge` принимает логин; регистрация
   занимает логин; таблица `logins` с уникальным индексом; лимиты по логину и по IP
   (через прокси). Тесты: два логина с одной пароль-фразой — разные аккаунты; занятый
   логин; неизвестный логин и неверная подпись дают одинаковый по времени отказ.
3. ✅ **Клиент.** `RemoteProfile`/`ServerProfile` получают логин; вывод identity с логином;
   вход и регистрация принимают логин; профиль хранит его для следующего запуска.
   Тесты: повторный запуск не спрашивает логин; биометрическая разблокировка тоже не
   спрашивает (логин лежит рядом с профилем, не секрет).
4. **Мастер настройки.** Первый экран: «У меня есть сервер» / «Настроить новый» →
   «Пропустить настройку». Для нового сервера — экран с комплектом развёртывания
   (ссылка на план 6) и выбором «Let's Encrypt / самоподписанный», без выпуска
   сертификата внутри приложения. Затем проверка URL и отпечатка, затем регистрация
   (логин, мастер-пароль, токен при необходимости).
5. **Смена сертификата.** Если отпечаток в профиле не совпал — диалог «сертификат
   изменился» с показом старого и нового, подтверждение руками; без подтверждения доступ
   не открывается.
6. **Миграция прототипа.** Аккаунты без логина: одноразовое «задайте логин» при входе
   или пересоздание (данные сейфа не меняются). Сервер при первом старте создаёт
   таблицу `logins` пустой — старые аккаунты продолжают работать через миграционный
   вход.
7. **Проверка на устройстве.** Вход по логину с ноутбука и с Android, сохранённый логин,
   биометрия, «Сменить хранилище» и повторный вход другим логином.

## Ограничения

- Закрытый ключ сертификата никогда не проходит через приложение и не попадает в логи.
- Приложение не умеет «отключить TLS»: `tls.required = false` остаётся сценарием
  локального сервера, а не следствием мастера.
- Логин — не секрет, но и не публичная информация: он уходит в URL/JSON запросов, поэтому
  rate-limit на вход обязателен.
- Пока протокол не изменён, работающий прототип не трогаем: правка протокола идёт одной
  согласованной серией коммитов (сервер + клиент + тесты), иначе старые сборки молча
  перестанут входить.
