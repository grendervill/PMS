# PMS Server — План 7: мастер настройки сервера

**Статус:** запланирован, **не реализован** (зафиксировано по просьбе пользователя 2026-11-19).
**Спека:** `docs/superpowers/specs/2026-11-18-server-sync-design.md` §18 — там же открытые вопросы.
**Предыдущие:** `2026-11-18-server-sync-01-server.md` … `-06-docker.md`.

## Что просит пользователь

При выборе серверного режима **первым этапом идёт настройка сервера**:

- этап **можно пропустить**, если сервер уже есть: ввести URL сервера, вход и
  мастер-пароль для доступа к хранилищу;
- при настройке нужно ввести URL и **выбрать SSL-сертификат на сервере**;
- должна быть возможность **сгенерировать самоподписанный сертификат через openssl на
  10 лет**, если человек сознательно не хочет публичный CA;
- **после этого** — регистрация пользователя на сервере и создание его хранилища.

Сейчас в приложении сделано проще: ввод URL, проверка сервера с показом отпечатка,
мастер-ключ, вход или регистрация. Мастера настройки и генерации сертификата нет.

## Предлагаемая последовательность шагов (черновик)

1. **«Сервер уже есть?»** — две кнопки: «У меня есть сервер» (сразу к URL и входу) и
   «Настроить новый». Пропуск — одно действие, без обязательных полей.
2. **URL** — адрес и порт; проверка живости (`/v1/healthz`), протокол, часовой пояс не важен.
3. **Сертификат** — три пути:
   - публичный CA (Let's Encrypt или коммерческий) — ничего не делать в приложении;
   - «сертификат уже установлен» — проверить и показать отпечаток;
   - «сгенерировать самоподписанный на 10 лет» — команда openssl с SAN и ключом
     3072 бита, результат кладётся туда, откуда сервер его читает (см. вопрос 1 спеки).
4. **Проверка** — `remote_probe` по введённому URL, показ отпечатка, предупреждение, если
   сертификат не от публичного CA, сохранение пина в профиль.
5. **Регистрация** — мастер-пароль, при необходимости токен регистрации; создание аккаунта
   и пустого хранилища; при существующем аккаунте — переход ко входу.
6. **Готово** — приложение открывает серверный режим, сейф создаётся в кэше и уезжает на
   сервер (это уже работает, план 3).

## Задачи (когда дойдёт до реализации)

1. **Решить открытые вопросы** §18 (где openssl, что значит «выбрать сертификат», нужен
   ли явный логин, ставит ли приложение сервер, что при смене сертификата, токен
   регистрации в мастере). Без этого планировать код бессмысленно: каждый ответ меняет
   объём в разы.
2. **Комплект для сервера** (если ставим не по SSH): архив с `compose.yaml`,
   `server.toml`, сгенерированным сертификатом/ключом и `README` на один экран;
   кнопка «Скачать комплект». Переиспользует план 6.
3. **Генерация сертификата**: команда openssl (RSA 3072 или ECDSA P-384, срок 3650 дней,
   `subjectAltName` из введённых DNS/IP), запись файлов в выбранную папку, права 600,
   закрытый ключ никогда не показывается и не пишется в логи.
4. **UI мастера** в духе `StorageModeScreen`: шаги, «Пропустить настройку» на первом
   экране, прогресс, ошибки текстом, отпечаток моно-блоком (стиль уже есть в форме профиля).
5. **Смена сертификата в профиле**: если отпечаток не совпал — отдельный диалог
   «сертификат изменился», показ старого и нового отпечатка, ручное подтверждение.
6. **Тесты**: юнит на генерацию аргументов openssl и разбор SAN; e2e на пропуск настройки
   и на полный путь с самоподписанным сертификатом против настоящего `pms-server`;
   визуальная проверка скриншотами (как требует AGENTS.md).

## Ограничения

- Ничего не делать по SSH без явного согласия: это доступ к чужой машине.
- Закрытый ключ сертификата не проходит через рендерер и не попадает в `localStorage`.
- Самоподписанный сертификат не отменяет требование TLS: `tls.required = true` остаётся.
- Мастер не должен уметь «отключить TLS» — это отдельный, явно небезопасный сценарий
  (`tls.required = false` только для локального сервера, как в §11).
