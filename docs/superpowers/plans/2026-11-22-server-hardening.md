# PMS Server — план 8: закалка и ускорение

**Статус:** реализован 2026-11-22 (P0, P1.1–P1.5, P2.1–P2.4). Результаты —
`docs/reports/2026-11-21-load-test.md`, раздел «Закалка».
**Основание:** вердикты ревью кода и нагрузочного лагеря —
`docs/reports/2026-11-22-server-review-verdicts.md`.
**Текущие ориентиры:** 5 056 PUT/s пик (C=32), 4.5–4.9k/s устойчиво, p50 6 мс / p99 12 мс,
1.45 ядра из 2, RSS 40–120 МиБ, чтение 12 742/s; логин деградирует 1186 → 395 op/s.

## Цели

1. **Потолок записи ≥ 12 000 PUT/s** и p50 ≤ 2 мс на той же VM — за счёт снятия
   `fsync` с критического пути (режим `batch` по умолчанию для контейнера,
   `always` для параноиков) и выноса SQLite с воркеров.
2. **Логин не деградирует**: ≥ 2 000 op/s и постоянное время на любом объёме сессий.
3. **Ни одного способа уронить сервер одним хостом**: дедлайны, лимиты, квоты, SIGTERM.
4. **Данные самовосстанавливаются**: после сбоя клиент всё равно может скачать сейф.
5. Всё измеримо: у каждой задачи есть критерий приёмки, который можно проверить тем же
   `allocbench`/`loadtest`, что уже есть.

## Этапы

### P0 — блокирующая безопасность (без этого не выкатывать)

**P0.1 Дедлайны запросов.**
- `server.rs`: `http_builder().http1().header_read_timeout(limits.header_read_timeout_secs)`
  и `first_request_timeout(то же)` для обоих режимов TLS.
- `api/mod.rs`: общий таймаут на **весь** запрос вокруг `put_vault`/`put_blob`/регистрации
  (`max(body_timeout_secs, len / min_bytes_per_sec)`), а не на кусок.
- `header_read_timeout_secs` и `body_timeout_secs` перестают быть мёртвым конфигом.
- Приёмка: тест «клиент прислал заголовки и молчит» → соединение закрывается за
  ≤ 2×`header_read_timeout_secs`; «тело по байту в 300 с» → 408/400 и убранный `.tmp`;
  занятый слот освобождается.

**P0.2 Лимитер и `nonces`.**
- Один ключ для `challenge` и `verify`: `account` (в `challenge` сначала резолвим логин,
  потом проверяем лимитер).
- `CREATE INDEX nonces_by_expiry ON nonces(expires_at)`; держать **один** активный nonce
  на аккаунт (`DELETE FROM nonces WHERE account_id = ?` внутри `insert_nonce`);
  глобальную чистку — раз в N вставок или фоновой задачей раз в 60 с.
- Приёмка: бенч «challenge+verify 60 с» даёт ≥ 2 000 op/s и **не падает** со временем;
  таблица `nonces` не растёт больше числа активных логинов.

**P0.3 Сессии: индекс, вытеснение, отзыв.**
- `CREATE INDEX sessions_by_expiry ON sessions(expires_at)`; prune-expired выполнять не на
  каждом входе, а раз в N вставок / по таймеру.
- Вытеснение по `rowid` (или `created_at`), а не по `expires_at` с секундной точностью.
- Новый маршрут `POST /v1/auth/session/revoke` (по предъявленному токену) + `revoke_all`
  уже есть; клиент вызывает его при «Отключиться».
- Приёмка: тест «два входа в одну секунду — вытесняется более старый по порядку»;
  `revoke` инвалидирует токен мгновенно; логин не деградирует после 50k сессий.

**P0.4 Удаление аккаунта: блокировка и свежесть подписи.**
- `Store::delete_account` берёт `account_lock`; при неудаче `remove_dir_all` возвращает
  ошибку и **не** удаляет строки индекса.
- Подпись удаления привязать к nonce (переиспользовать challenge) или к заголовку
  `x-pms-timestamp` с окном ±120 с и записью `last_delete_at`.
- Приёмка: тест «PUT в полёте + DELETE» → либо PUT отбит, либо каталог удалён целиком,
  третьего состояния нет; повтор записанной подписи через 10 минут → 401.

**P0.5 Квоты и диск.**
- Учитывать `staging/` (счётчик `AtomicU64` в `AppState`, декремент в `Drop` у `Staged`).
- Проверять свободное место (`statvfs`) перед приёмом тела.
- Квота: помимо объявленного `Content-Length`, проверять фактически принятые байты.
- `max_connections` по умолчанию 128 (512 — только с `mem_limit ≥ 512m`), в compose
  добавить `ulimits.nofile` и `stop_grace_period`.
- Приёмка: тест «N параллельных загрузок упираются в квоту», «staging-мусор не превышает
  лимит», «отказ при < 1 ГиБ свободного места».

**P0.6 Оракул логина и тексты ошибок.**
- `challenge` на неизвестный логин отвечает так же, как на известный (nonce от случайного
  `AccountId`), а различие остаётся только в `verify` (единый 401).
- Убрать `error.to_string()` из ответа `POST /v1/accounts`; убрать `info!` на каждый
  неизвестный логин.
- Приёмка: тест «ответы challenge для известного и неизвестного логина совпадают по коду
  и размеру тела», «внутренние ошибки не содержат путей».

### P1 — скорость

**P1.1 SQLite вне воркеров и без лишних парсов.**
- `Arc<Mutex<Connection>>` + приватные blocking-методы; публичные `Store::*` становятся
  `async` и делегируют в `spawn_blocking` (по образцу `api/account.rs`).
- `prepare_cached` для `session()`, `blob_info()`, `usage()`.
- Пул 2–4 read-only соединений для `session`/`account`/`blob_info` (WAL это позволяет),
  один писатель.
- Приёмка: p99 смешанной нагрузки (PUT 90 % + auth 10 %) снижается ≥ 30 %; воркеры tokio
  не блокируются (замер «худший тик планировщика» < 2 мс).

**P1.2 `fsync`: политика, батчинг, `sync_data`.**
- `[limits] fsync = "always" | "batch" | "none"` (по умолчанию `batch` в контейнере,
  `always` для локальной установки).
- `sync_data()` вместо `sync_all()` (дешевле на ext4), fsync каталога — только в `always`.
- `batch`: одна фоновая задача раз в 1–5 мс делает `fdatasync` по «грязному» набору;
  ответ клиенту — после постановки в набор, `version` гарантирует порядок.
- Приёмка: при `batch` p50 ≤ 2 мс и ≥ 10 000 PUT/s; при `always` цифры не хуже текущих;
  тест «версии не переставляются местами после падения».

**P1.3 Регистрация в один проход.**
- `put_vault` умеет принимать готовый staged-файл: `rename` вместо повторной записи и
  повторного BLAKE3, доверяя `staged.digest()`.
- Приёмка: регистрация с сейфом 3 МиБ: одна запись, один fsync, один хеш;
  ≥ 1 500 аккаунтов/с.

**P1.4 Блобы и чтение.**
- Один запрос `SELECT …` с `prepare_cached` вместо 2–3; `bump_blob_use` — только если
  `last_used_at` старше часа (чтения перестают писать в WAL).
- `GET /v1/vault`: блокировка аккаунта на время `account()` + `File::open` (микросекунды).
- Приёмка: `GET /v1/vault` ≥ 15 000/s; «10 000 чтений подряд» не добавляют WAL-записей.

**P1.5 Мелкие аллокации и буферы.**
- Буфер хеширования по размеру тела (`vec![0; min(CHUNK, len)]`) вместо 64 КиБ на стеке.
- Проверка версии протокола без `to_string()` на каждый запрос.
- TLS ticketer + `ServerSessionMemoryCache` (повторные подключения без полного
  рукопожатия).
- `account_lock`: LRU или удаление записи при удалении аккаунта.
- Приёмка: `allocbench` — PUT ≤ 60 аллокаций при том же числе реаллокаций;
  RSS на C=128 ≤ 100 МиБ.

### P2 — целостность и эксплуатация

**P2.1 Самовосстановление сейфа.** В `recount`: если размер файла не совпал с индексом —
перечитать файл, посчитать BLAKE3 и **обновить дайджест** (файл — истина), версию не
менять. Приёмка: тест «подменить файл, рестарт → клиент скачивает и получает совпадающий
дайджест».

**P2.2 Сверка блобов в обе стороны.** Файлы без строк — удалить (или принять в индекс),
строки без файлов — удалить. Приёмка: «осиротевший блоб не занимает квоту».

**P2.3 Уборка `staging/` на старте + SIGTERM.** Приёмка: после `docker compose stop`
временных файлов нет, процесс выходит за ≤ 5 с.

**P2.4 Порядок и полнота бэкапа.** `backup.sh`: снимать индекс **после** данных или
блокировать запись на время снимка; в README — честная процедура восстановления
(уже описана, добавить сверку дайджеста после реставрации).

## Порядок и проверка

1. P0 целиком (это безопасность) → прогон тестов + ручная проверка slowloris-сценария.
2. P1.1 и P1.2 (главный выигрыш) → повторный лагерь: те же 6 сценариев, сравнение таблиц.
3. P1.3–P1.5, затем P2.
4. Финальный отчёт: таблица «до/после» по каждому критерию приёмки и обновление
   `docs/reports/2026-11-21-load-test.md`.

## Чего в этом плане нет (сознательно)

- Смена HTTP-стека, io_uring, собственные SIMD-ядра: замеры показывают, что предел —
  диск и SQLite, а не цикл обработки.
- Шардирование SQLite по аккаунтам: сначала смотрим, сколько даёт P1.1/P1.2; шардирование
  остаётся козырем, если после них упрёмся в один писатель.
- Поштучная синхронизация, шаринг, админ-панель, ACME — вне v1 по спеке.
